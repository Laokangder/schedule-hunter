# 日程猎人十项功能并行开发计划与 TODO

> 创建日期：2026-10-16
> 状态说明：本文是开发计划，不代表功能已经完成。完成状态必须以代码、自动化测试和 Android 真机验收结果为准。

## 一、范围

本轮统一实现以下十项能力：

| 编号 | 功能 | 优先级 | 当前基础 | 完成标准 |
|---:|---|---|---|---|
| 1 | 候选日程收件箱 | P0 | 已有前台候选状态和原生捕获队列 | 候选可持久化展示，并支持确认、编辑、忽略 |
| 2 | 日程编辑与改期 | P0 | 前端已有更新调用与本地通知重建能力，后端缺少完整接口 | 更新成功后旧提醒取消、新提醒重建，刷新后数据一致 |
| 3 | Android 分享入口 | P0 | 解析接口已支持 `input_type=intent` | 其他 App 的文本可分享进日程猎人并生成候选 |
| 4 | 通知快捷操作 | P1 | 已有后台候选通知 | 通知提供确认、稍后处理和忽略入口，动作幂等 |
| 5 | 变更猎人 | P1 | 已有任务列表与解析能力 | 能识别改期、换地点和取消，并关联已有任务后要求确认 |
| 6 | 系统日历同步 | P1 | 尚未接入 Calendar Provider | 用户确认后可写入系统日历，改期和删除保持一致 |
| 7 | 相似候选合并 | P1 | 原生层已有短时间内容指纹去重 | 同一活动的重复通知合并为一个候选，并保留出现次数和来源 |
| 8 | 候选稍后提醒 | P1 | 尚未实现 | 候选可延后 10 分钟或 1 小时，到期后重新提示 |
| 9 | 智能空档推荐 | P1 | 已有基础冲突检测和固定顺延建议 | 扫描真实空闲区间，返回至少三个可执行候选时间 |
| 10 | 通知来源管理 | P1 | 已有通知读取总开关和敏感内容过滤 | 支持按应用允许或禁止监听，默认遵循最小权限 |

## 二、统一业务闭环

```text
通知监听 / Android 分享 / 手动输入
                ↓
           AI 解析与变更识别
                ↓
      候选持久化与相似候选合并
                ↓
候选收件箱 ── 编辑 / 忽略 / 稍后提醒
                ↓
         冲突检测与智能空档推荐
                ↓
        用户确认创建或更新日程
                ↓
 Android 本地提醒 + 系统日历同步
```

任何自动捕获内容都只能先生成候选，不允许在没有用户确认的情况下直接创建、修改或取消正式日程。

## 三、统一候选数据模型

后端候选记录至少包含：

| 字段 | 说明 |
|---|---|
| `candidate_id` | 候选唯一 ID |
| `request_id` | 请求幂等 ID，必须唯一 |
| `dedup_key` | 服务端生成的候选合并键 |
| `intent_type` | `create`、`update` 或 `cancel` |
| `target_task_id` | 变更候选关联的原任务，可为空 |
| `source_type` | `notification`、`intent` 或 `manual` |
| `source_package` | Android 来源包名，可为空 |
| `source_app_name` | 用户可读的来源应用名称 |
| `source_text` | 原始文本；日志中不得输出 |
| `parsed` | 标题、时间、地点、参与者等解析结果 |
| `changes` | 变更前后字段差异 |
| `confidence` | 解析或匹配置信度 |
| `status` | `pending`、`snoozed`、`confirmed`、`ignored` |
| `snoozed_until` | 稍后提醒时间，可为空 |
| `seen_count` | 相似候选累计出现次数 |
| `sources` | 合并后的来源摘要数组 |
| `created_at` / `updated_at` | 创建和更新时间 |

合并规则：

1. 相同 `request_id` 必须幂等返回同一候选。
2. 原始内容指纹完全相同时直接合并。
3. 标准化标题相同、开始时间相差不超过 10 分钟且地点相同或一方为空时，合并仍处于 `pending/snoozed` 的候选。
4. 合并后增加 `seen_count`、更新 `updated_at` 并追加来源摘要。
5. 新解析结果置信度更高时才替换主解析结果。
6. `confirmed/ignored` 候选不因后续普通重复通知重新打开；明确的改期或取消信息应建立变更候选。

## 四、接口契约

后端窗口负责实现并测试以下接口：

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/v1/tasks/{task_id}` | 查询单个正式日程 |
| `PUT` | `/api/v1/tasks/{task_id}` | 编辑或改期，支持部分字段更新 |
| `POST` | `/api/v1/candidates` | 幂等创建或合并候选 |
| `GET` | `/api/v1/candidates` | 按状态查询候选收件箱 |
| `GET` | `/api/v1/candidates/{candidate_id}` | 查询候选详情 |
| `PATCH` | `/api/v1/candidates/{candidate_id}` | 编辑候选字段或设置状态 |
| `POST` | `/api/v1/candidates/{candidate_id}/confirm` | 确认创建、更新或取消正式日程 |
| `POST` | `/api/v1/candidates/{candidate_id}/snooze` | 延后 10 分钟、1 小时或指定时间 |
| `POST` | `/api/v1/tasks/free-slots` | 根据日程和工作时间推荐空档 |

统一要求：

- 所有写接口必须支持 `request_id` 幂等。
- 返回继续使用项目现有 `BaseResponse`。
- 不存在统一返回业务码 `4001`。
- 时间非法统一返回业务码 `2001`。
- 确认候选必须在单个事务内完成任务写入和候选状态更新。
- 改期后清空 `reminded_offsets` 并重置 `is_reminded`。
- 变更成功后发送现有 `TASK_UPDATED` WebSocket 消息。

## 五、智能空档第一版规则

第一版不接地图和交通 API，仅使用本地正式日程：

1. 输入期望时长、搜索开始与结束时间、工作时段和缓冲分钟数。
2. 忽略 `completed`、`expired` 和 `cancelled` 日程。
3. 将已有日程前后扩展缓冲时间后合并占用区间。
4. 从剩余空档中选择可容纳期望时长的区间。
5. 至少返回“最早可用”“最接近原时间”“当天影响最小”三个排序结果；不足三个时返回实际数量。
6. 返回值必须包含开始时间、结束时间和推荐理由。

## 六、两个窗口的职责边界

### 当前窗口：前端与 Android

- 候选收件箱页面、候选详情和确认/编辑/忽略交互。
- 日程编辑与改期 UI，成功后重建 Android 本地通知。
- Android `ACTION_SEND` 文本分享入口。
- Android 候选通知的确认、稍后处理和忽略快捷按钮。
- 系统日历授权、写入、改期和删除同步。
- 来源应用列表、允许/禁止规则和本机持久化。
- 相似候选、变更猎人和智能空档结果的前端展示。
- 只修改 `frontend/src` 和 `frontend/android`；本轮不修改后端文件和主计划文档。

### 另一个窗口：后端与文档

- 候选表、Repository、Service、API 和数据库兼容迁移。
- 单任务查询与部分更新接口。
- 候选幂等、相似合并、稍后提醒到期查询。
- 变更意图模型、原任务匹配和确认事务。
- 智能空档算法与接口。
- 后端单元/集成测试。
- 根据实际实现更新本文件及项目进度文档。
- 只修改 `backend` 和 `docs`，不修改任何前端或 Android 文件。
